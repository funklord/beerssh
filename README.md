# BeerSSH

Copyright (C) 2026 Nabeel Sowan <nabeel@vibes.se>

An SSH terminal for **Android and desktop** — background sessions, tabs,
adaptive splits, and a real keyboard. Qt Widgets, C++, one codebase for
both platforms.

Status: **verified against a real host.** The app connects over SSH,
authenticates with a password, opens a PTY channel, and renders the result
through a real VT emulator — colours, attributes, cursor addressing,
scrolling and CJK double-width cells all work:

```sh
./beerssh user@host        # tries your SSH key, asks for a password only if it fails
```

Public-key authentication is tried first — the agent, then your default
identities — so a key-authenticated session holds no credential at all and
reconnects on its own after a network drop. If a key exists but does not
get in unaided it offers to unlock it, because for a server that only
accepts keys a password prompt is not a fallback but a prompt that cannot
succeed. The passphrase is used and not kept.

**It takes xterm's and konsole's arguments**, because a terminal that opens a
local shell has to answer to the vocabulary people already have:

```sh
beerssh                          # a local shell
beerssh user@host:2222           # a shell on that host
beerssh -e htop                  # a local shell running htop
beerssh user@host -e htop        # htop over there, as `ssh -t` runs it
beerssh --workdir /srv -T Logs -e tail -f app.log
beerssh --geometry 120x40        # cells, as xterm counts them -- not pixels
beerssh --load "prod bastion"    # a saved session, by name
```

`--hold` keeps a pane after the command exits, `--help` lists the rest, and
everything after `-e` belongs to the command. `man beerssh` documents the lot
— the page is generated by the program from the same table its options are
parsed from, so it cannot describe a flag beerssh does not take. The bash
completion comes from that table too, so `beerssh --<TAB>` offers exactly
what the parser accepts. A shell that ends closes its
pane — and the window with it, if that was the last one. `project.md` §8.6
records the whole set, including why Qt's own toolkit options are no longer
accepted on the command line (its X11 plugin was eating `--geometry` and
`--title` before the program saw them, and no other plugin did).

**The desktop furniture is configurable**, under *This device*: a scrollbar
(automatic, left, right or hidden — automatic means wherever there is a pointer
to drag it with), what the status line says or whether it says anything, the
window-title format (`%t - BeerSSH` by default, with `%n %u %h %p %a` available),
and every chord this app keeps for itself. `Ctrl+Shift+T` and `Ctrl+Shift+N` open
another session in a tab or a window. **Clear a chord and it goes back to the
remote shell** — whatever BeerSSH keeps, your shell never sees.

**On desktop it opens a local shell by default**, so launching it with no
arguments gives you a terminal rather than a connection dialog. That was a
documented non-goal until it was deliberately reversed: the PTY is a
`bssh_ssh_session` implementation like any other transport, so the emulator,
the renderer, the input router and the scrollback still know nothing about
one. Android gets no local shell — an unprivileged app sandbox has no useful
userland, which is what Termux exists to supply — and opens its configuration
instead.

Typing works: keys, modifiers, function keys, arrows in both normal and
application-cursor mode, Meta/Alt, bracketed paste (`Ctrl+Shift+V`), and
input-method commit text. The on-screen key row for touch devices is
built on every platform but hidden unless touch is the primary input.

OSC 8 hyperlinks are underlined and open on `Ctrl+click`, after showing you
the address — a URL chosen by the remote host should not open on a stray
tap. Synchronized output (DEC 2026) is honoured, so a full-screen program that
brackets its redraw is painted in one frame rather than mid-update.

Modern keyboard protocols are supported so full-screen programs can tell
`Ctrl+I` from `Tab` and `Alt+x` from `Escape`-then-`x`: the **kitty keyboard
protocol** (disambiguate tier, with push/pop/set/query) and **xterm
`modifyOtherKeys` level 2**. `project.md` §7.1 surveys the wider set of
modern terminal extensions and says where each one stands.

Inline images work for all three protocols: the **kitty graphics
protocol**, **iTerm2 inline images** and **sixel** — `kitten icat`,
`imgcat` and `img2sixel` style output all render. Needs `libsixel-dev`
(Debian/Ubuntu) alongside Qt and libssh.

Scrollback works — mouse wheel or `Shift+PageUp`/`PageDown`, capped at 5000
lines by default, keeping colours and attributes. Typing returns to the
live screen. The alternate screen is honoured, so `vim` and `less` leave
your shell output as they found it.

Mouse works: drag to select, double-click for a word (paths included),
triple-click for a whole line,
`Ctrl+Shift+C` to copy, middle-click paste via the primary selection on
X11/Wayland. When a full-screen program asks for the mouse it gets the
clicks instead — hold `Shift` to select anyway.

**Zoom** with `Ctrl+=`, `Ctrl+-` and `Ctrl+0`, or `Ctrl`+wheel, or from the
right-click menu — which is how a phone reaches it. It moves the text of the
session in front of you, on top of whatever size that host resolves to, and
`Ctrl`+wheel works inside `less` and `vim` too, where the remote otherwise
owns the wheel. It is not saved: a size you want every time is the host's own
font setting.

**The terminal's own menu is where a phone reaches everything else** —
right-click on a desktop, press and hold on a touch screen. Find in the
scrollback, text size, the panes, and the session verbs: another tab or
window, duplicate this host, connect a session that is not live, and close
one. It also clears the scrollback and resets the terminal, which are the two
things a wedged or dropped session cannot ask its shell to do — `clear` and
`reset` both need a shell that is listening.

Most of those have a chord or a menu-bar entry on the desktop as well. The
menu exists because a phone has neither, and because a tab bar it could have
used is not drawn when every session is already on screen in the column.

Closing the window with a session still connected asks whether to keep it
running in the background or disconnect and quit, and remembers the answer.
On desktop "background" means a tray icon and a process that outlives its
window; on Android it means a foreground service and `moveTaskToBack`. The
two are not the same operation, and assuming they were cost the Android
build its way back in: a hidden top-level widget there leaves the launcher
resuming an Activity that never shows itself again.

Multiple sessions work: each lives in a registry rather than in a widget,
with a tab bar that appears once there is more than one. Switching tabs
re-points the view at another session's screen — nothing is copied, and a
session keeps running (and keeps receiving output) while nothing is
showing it.

A tab can be **torn out into a window of its own**. The session registry is
process-wide, so a second window is another view onto the same sessions
rather than a second copy of them, and a session showing in neither keeps
running. Focus-follows-mouse is available and off by default.

Split panes follow the window, not the platform: under 600dp it is tabs
only, up to 840dp two panes, above that four. Narrowing the window
collapses the extra panes back to tabs **without closing or disconnecting
anything**, and widening restores the arrangement. The focused pane carries
a border whenever there is more than one — two identical shells side by
side is a real footgun otherwise.

Dropped connections retry on their own: exponential backoff, capped and
jittered so several sessions dropped by one network flap do not all
reconnect in the same millisecond, and an immediate retry when the network
changes (a laptop waking from suspend is the common case). A disconnect
you asked for is never retried.

**A reconnect is a new remote shell.** Plain SSH cannot resume one, so the
running program and working directory are gone; only the local scrollback
survives. Attaching to `tmux` on connect is the available answer until
Mosh is considered in v2.

`Ctrl+Alt+Left`/`Right` move focus between panes, and the status line
reports reconnection as it happens rather than leaving a silent terminal
that looks identical to a quiet one.

Each tab carries a status dot — connected, connecting, disconnected, or a
bell that rang while you were looking at another tab. Dragging a divider
snaps to whole character cells, so no pane renders half a glyph at its
edge.

Which hosts were open, how they were arranged and which was active are
remembered across restarts. The connections are not — plain SSH cannot
resume a shell — so the front door reopens with the last host selected
rather than pretending to have restored anything.

Not built yet: general key remapping (`project.md` §6.1), a user-composed
key row (§6.2), reopening every remembered host at once (§8.4), and the
shared glyph atlas (§9.5). SFTP, port forwarding and Mosh are deliberate v1
non-goals rather than omissions — §1 says why, and §5.3 says what plain SSH
cannot promise about a resumed shell.

A password can be remembered per host — off by default, and only for a
saved host, since the secret is keyed to it. Remembered passwords are
replayed on reconnect, so a password-authenticated session survives a
network drop without holding the credential in memory the whole time.

Credentials go to the **system keyring** (GNOME Keyring, KWallet, anything
speaking Secret Service) when one is actually running — no extra
passphrase, since your login session already unlocked it. Where none
answers, they go to a passphrase-encrypted file
(`~/.local/share/beerssh/secrets.enc`, PBKDF2 + AES-256-GCM via OpenSSL).
The choice is made at runtime, and the UI names the backend rather than
calling everything "encrypted" — a passphrase file and a session keyring
are not the same promise.

Host keys are shared with `ssh(1)` rather than kept apart from it. All of
`~/.ssh/known_hosts`, BeerSSH's own store and `/etc/ssh/ssh_known_hosts` are
read, so a revocation in any one of them is a revocation. An accepted key is
appended to `~/.ssh/known_hosts` **hashed** — `|1|salt|HMAC-SHA1`, which is
what OpenSSH's own `HashKnownHosts` default writes — and falls back to
BeerSSH's store where that file cannot be written, as on Android. An unknown
host shows its fingerprint and waits for you to accept before anything is
written; a *changed* key gets a louder, differently-worded warning and
defaults to cancelling.

A host can be reached **through a jump host** (OpenSSH's `ProxyJump`), with
the protocol to the target running end-to-end inside the tunnel rather than
the bastion seeing it. Hosts can be **imported from an OpenSSH config**,
the key file each one names included.

A curated set of terminal fonts ships with the app, vetted for monospace
metrics and glyph coverage, with a fallback chain ending at Unifont so that
no output is ever unreadable. Colour schemes are chosen per host. The window
follows the system's light or dark preference — asked for over the XDG
portal on Linux and from `Configuration.uiMode` on Android, because Qt alone
answers `Unknown` on the one and goes stale on the other. The terminal's own
colours deliberately do not follow it: a dark terminal in a light window is
a choice somebody made, not a bug. A screen reader can read the terminal,
scrollback and selection included.

See `project.md` §14 for the milestone plan.

## beersshd

A second, separate program from this tree: an SFTP server and nothing else.
It serves one folder to the keys in one authorized-keys file — no shell, no
commands, no passwords — and is meant for an Android phone, where it will
be its own app so that the permission to reach shared storage belongs to a
file server rather than to the terminal. On the desktop it is a command
line:

```sh
./beersshd --root ~/Public --port 8022
sftp -P 8022 phone-or-host          # or: scp -P 8022 file host:
```

On Android it is its own app, `se.vibes.beersshd`, built with
`make android-sshd` (and `android-sshd-install`): it asks for All files
access, serves shared storage on the phone's Wi-Fi address, and takes its
authorized keys from a box on its one screen.

The host key is generated on first start under `~/.config/beersshd/`, and
keys are read from `~/.config/beersshd/authorized_keys` at every login.
Modern `scp` works, since it speaks SFTP; `scp -O` does not. A path that
leaves the folder — by `..` or through a symlink — is refused. See
`project.md` §19.

## Presets

A preset is a reusable set of terminal settings — `TERM`, scrollback,
colours, keepalive, an on-connect command — attached to many hosts, so
editing one changes all of them. Six starter presets ship (Default Linux,
Raspberry Pi/SBC, OpenWrt/BusyBox, BSD, network switch, tmux-first), and a
host may override any single field with a one-click revert.

**A preset is structurally incapable of holding a secret** — no hostname,
username, password or key reference — so exporting one and sending it to a
colleague cannot leak your infrastructure. That is enforced by the type
having nowhere to put such a thing, and asserted by a test on the exported
keys.

## The interface

Two front doors over one set of saved hosts (`project.md` §8.5):

- **Desktop borrows PuTTY's layout** — category tree, destination at the
  top, saved sessions with Load/Save/Delete. Familiar without instructions
  if you have ever used PuTTY.
- **Touch gets a mobile list** — full-bleed rows, one tap to connect, a
  floating add button, kinetic scrolling, and a full-screen form (not a
  dialog) for adding a host.

Which appears follows the input device rather than the OS, so a
convertible in tablet mode gets the touch one. Hosts live in
`~/.ssh/beerssh_hosts` — an INI file, beside the rest of your SSH material
and named after `known_hosts` so it says what is in it — with presets,
layout and device settings in the app's own config directory. None of those
files has anywhere a credential could go; secrets live only where the
paragraphs above put them.

## Build (desktop)

Needs Qt 6 (6.8 LTS or newer), CMake, and a C++17 compiler. On
Debian/Ubuntu that is:

```sh
sudo apt install build-essential pkgconf cmake qt6-base-dev \
                 libssl-dev libsixel-dev libsecret-1-dev zlib1g-dev
```

**One Qt package covers it.** The app asks for `widgets network dbus` and
the tests add `testlib` — all of them Qt Base — so `qt6-base-dev` is the
whole Qt requirement, and it brings `qmake6`, `qt6-base-dev-tools` (moc,
uic, rcc) and `qt6-qpa-plugins` with it. Nothing outside Qt Base is used
and there is no QML runtime, which is also why the APK is as small as it
is.

The rest answer the `PKGCONFIG` and `LIBS` lines in `beerssh.pro` one
for one:

- `cmake` — builds libssh, which is not a system package here: it is the
  `libssh/` submodule, linked statically with this tree's patches applied
  (`project.md` §8.4), and `make` fetches and builds it.
- `libssl-dev` — `libcrypto`, libssh's crypto backend, and for the
  passphrase-encrypted secret file and for sealing pictures spilled to
  disk (`project.md` §7.1).
- `libsixel-dev` — sixel images (`project.md` §7.2).
- `libsecret-1-dev` — the Secret Service keyring.
- `zlib1g-dev` — `-lz`, for libssh, for the zip reader that fetches a font on a phone
  file by file (`project.md` §9.4), and for compressing spilled pictures.

Two of these are worth naming even though a build often works without
naming them. `libssl-dev` used to arrive as a dependency of `libssh-dev`,
and **nothing at all pulls in `libsecret-1-dev`** — it was satisfied here
for months only because the CI runner image happened to carry it, which
`project.md` §18 records. A build that leans on a package no file names
fails one image update later, with a pkg-config error that reports the
library and not the fix.

libvterm is vendored as a submodule and built from source. **You do not
have to remember `--recurse-submodules`** — a build that needs libvterm
and cannot find it fetches the submodule itself, once. `make style` and
the other targets that do not need it never reach the network. The build
then applies the patches in `vterm-patch/`; `make veryclean` reverts
them. See `project.md` §7.1 for what they fix and why they are not
committed into the submodule.

```sh
make          # build ./beerssh and ./beersshd
make run      # build and run it
make test     # smoke test + unit tests (offscreen QPA, no server needed)
make check    # the umbrella: everything that must pass before committing
make style    # the shared style gate, copied verbatim from the source
make hooks    # install the git hooks, commit-msg among them
make shots    # render every screen to PNG, because looking at it is the test
make deb      # Debian packages, built with debhelper from VERSION
make bench    # emulator throughput in MB/s; not a gate, run it on an idle box
```
Or with [fmake](../fmake), which needs no build file and nothing beyond the
Python standard library:

```sh
python3 ~/src/fmake/fmake   # ./beerssh, same sources
```

**Not `/usr/bin/fmake`.** The packaged one predates `$file()` and leaves the
reference in the value as text, so the build succeeds and the binary
carries the literal string. Measured: `--version` printing
`$file(VERSION)`. Run the one in fmake's own tree until a newer package is
installed.

**Run `make` first, or at least its vterm step.** fmake compiles the
submodule from source and the patches in `vterm-patch/` are not committed
into it, so a tree where they have not been applied fails on
`VTERM_PROP_RESET` — which is §7.1 working as designed rather than a
problem with either build.

**It works in a tree where `tool/build-deps-android.sh` has run, since
fmake's §305.** It did not: `fmake.toml` excludes `build-deps-android`,
which kept its sources out of the build while the exclusion did not reach
the include path, so libssh's headers shadowed the C library's
`<string.h>` and every file including a Qt header failed. Signalled as
fmake's §293 and settled there on 2026-09-21 in `06d2c26`, which filters
the include set the graph infers as well as the sources.

**Measured here rather than taken on report**, in this tree with the
dependency build present, by the method §293 itself used — a dry run,
`python3 /home/funk/src/fmake/fmake -n -v`, counting `-I` directories
under `build-deps-android`. **No compile line carries one.** §293 counted
109; the compiler's include path is clean.

`fmake.toml` says what fmake cannot read off the tree: the version, from
`VERSION` rather than written a third time; `BSSH_TEST_FONT_DIR`, which
`test/tests.pro` passes and the font catalogue test reads;
`QT_QPA_PLATFORM=offscreen`, which the test program needs and the `test`
target already sets; `vterm/include`, which qmake carries as
`INCLUDEPATH` and without which every `bssh_emulator` method is missing at
the link; and that the Android translation units, the Android dependency
trees and `build-*` are not part of a desktop build. `make` remains the
interface — fmake builds the program and none of the gates, the APK or the
packaging.


`make` wraps qmake, which does the actual Qt build in `build/`; everything
else in the tree is a plain Makefile. `make help` lists the targets.

### The Debian packages

`make deb` builds with `dpkg-buildpackage` and debhelper, taking the
version from `VERSION`, and collects two into `build/`:

- **`beerssh`** — the program, its manual page, its bash completion, the
  desktop entry, the icons and the AppStream metadata.
- **`beerssh-fonts`** — the curated terminal fonts and their licence
  texts. A `Recommends` rather than a `Depends`: without it the app falls
  back to the system monospace fonts and still runs.

debhelper also emits **`beerssh-dbgsym`**, the detached debug symbols,
collected into `build/` alongside the other two.

`debian/control` is where the build-time list above is declared, and it
must stay in step with `beerssh.pro`'s `PKGCONFIG` lines. **Runtime
dependencies are not written by hand** — `dpkg-shlibdeps` computes them
from what the binary actually links, which is the main reason packaging
goes through `dpkg-buildpackage` rather than `dpkg-deb` or CPack.
`make check-deb` installs the built packages in a container and checks
the result, the manual page and a headless `--help` among it.

## Build (Android)

Needs a Qt-for-Android kit and an NDK, neither of which the desktop build
requires:

```sh
export ANDROID_NDK_ROOT=$HOME/android-ndk-r29
tool/build-deps-android.sh arm64-v8a          # cross-builds libssh + OpenSSL
make android QT_ANDROID_ROOT=$HOME/Qt/6.11.1/android_arm64_v8a
```

Verified for `arm64-v8a` and `x86_64` (the emulator's ABI). Packaging into
an APK additionally needs the Android **SDK**, which is separate from the
NDK.

No Qt account is needed for the kit — `aqtinstall` fetches the same
official binaries:

```sh
python3 -m venv ~/.venv/aqt && ~/.venv/aqt/bin/pip install aqtinstall
~/.venv/aqt/bin/aqt install-qt linux desktop 6.8.2            # host tools
~/.venv/aqt/bin/aqt install-qt linux android 6.8.2 android_arm64_v8a
```

**It runs, and it connects.** Built, packaged and driven on an Android 11
x86_64 emulator: the touch front door appears, the on-screen key row shows
itself because touch is the primary input, adding a host writes the config
store, and SSH reaches a real server — key exchange, the trust-on-first-use
prompt showing the correct fingerprint, the key written to the device's own
known-hosts store, then key auth attempted and a password requested. The
debug APK is 18.6 MB with no QML runtime and no permissions beyond INTERNET
and ACCESS_NETWORK_STATE.

Backgrounding works: a foreground service starts with the first session and
stops with the last, so sessions survive the home button. The notification
it must show reports the session count.

A session has been carried through to a live shell and survived an
orientation change: a marker was left in the scrollback, the emulator
rotated, and the same scrollback found on the other side (`project.md`
§8.2, which also records the two steps of that test still unverified).

Not yet settled on Android: the emulator runs API 30, where Android 14's
foreground-service type rules are not enforced, so the `connectedDevice`
choice has never actually been adjudicated and Play review's opinion of the
framing is unknown. Still unexercised on real hardware: a physical keyboard,
and steps 2 and 3 of the rotation test.

## Layout

```
beerssh.pro          qmake project — the app, both platforms
beersshd.pro         qmake project — beersshd, the SFTP-only server (§19)
android-sshd/        beersshd's AndroidManifest.xml and its service shim
Makefile             top-level: wraps qmake, plus everything non-Qt
src/main.cpp         entry point (--self-test is what CI runs)
src/ui/              widgets: main window, terminal grid
src/ssh/             bssh_ssh_session -- the SSH transport, behind an interface
src/term/            bssh_screen + the libvterm-backed emulator
src/input/           bssh_input_router -- every keystroke becomes bytes here
vterm/               vendored libvterm (submodule, MIT, upstream untouched)
src/platform/        bssh_platform + one implementation per platform
src/model/           the session registry, host/preset stores, reconnection
src/sshd/            beersshd: the server, its SFTP handlers, its root
test/               host unit tests + the fake SSH session they drive
android/             AndroidManifest.xml and the service shim
debian/              debhelper packaging; VERSION at the root is the source
vterm-patch/       applied to the submodule at build time, not committed to it
tool/               the style gate, the git hooks, and the check-* scripts
```
